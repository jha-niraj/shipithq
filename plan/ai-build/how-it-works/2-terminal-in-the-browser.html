Chapter 2

The terminal in the browser

A browser can't run bash. It doesn't need to. bash runs in the container; the browser only draws characters and sends keystrokes. Between them is a fake terminal on one end and a live connection in the middle.

First: what a terminal actually is

Forget the browser for a minute. On your Mac, when you open Terminal and type ls, two separate programs are involved:

  • The terminal window (Terminal.app, iTerm, the one in VS Code). It only does two things: it sends the keys you press, and it draws whatever characters it receives. It has no idea what ls means.
  • The shell (bash, zsh). It reads keys, understands commands, runs programs, and writes text back.

Between them is a terminal device: a two-way pipe the shell believes is a real keyboard and screen. Programs check for one; it is how ls knows to print in colour and how Claude Code knows it can draw its full-screen interface.

So "a terminal in the browser" means: replace Terminal.app with a web page (xterm.js), keep bash, and give bash a fake terminal device (a PTY) whose other end is a WebSocket instead of a window.

One keystroke, all the way there and back

You type l. Here is everything that happens before the l appears on your screen. Note the surprise in step 6: the browser does not print the l when you press it. bash sends it back, and only then is it drawn. That echo is why typing feels instant on a fast connection and laggy on a slow one.

    ws.onopen = () => ws.send(JSON.stringify({ t: "r", c: term.cols, r: term.rows }))  // "I am 120 x 32"
    ws.onmessage = (m) => term.write(m.data)                          // whatever bash says, draw it

connect()
term.onData((d) => ws.send(JSON.stringify({ t: "i", d })))          // every key you press, send it

Two message types travel up: {"t":"i"} is input (keys), {"t":"r"} is resize (the box changed size, so bash and Claude can redraw to fit). Down comes plain text.

2. On your Mac: the host server connects the two calls

The browser's call reaches the host server. The host server makes a second call to the container and joins them, like an operator patching two phone lines.

apps/sandbox/src/server.ts

server.on("upgrade", (req, socket, head) => {
    // Only "/s/<session id>/pty" is allowed to become a WebSocket.
    const m = new URL(req.url, "http://host").pathname.match(/^\/s\/([a-f0-9]{8})\/pty$/)
    const meta = readMeta(m[1])                                   // which door? 32771
    wss.handleUpgrade(req, socket, head, (browser) => {
        const up = new WebSocket(`ws://127.0.0.1:${meta.port}/pty`) // call the container
        up.on("message", (d) => browser.send(String(d)))           // container -> browser
        browser.on("message", (d) => up.send(String(d)))           // browser -> container
        up.on("close", () => browser.close())                      // one hangs up, both hang up
        browser.on("close", () => up.close())
    })
})

3. In the container: the fake terminal and bash

This is the only part that is new to most people. pty.spawn starts bash attached to a fake terminal device and gives us both ends of it: term.write() types into it, term.onData() hears what comes out.

apps/sandbox/image/agent/server.mjs

import pty from "node-pty"

let term = null
let scrollback = ""
const clients = new Set()                 // every open browser tab on this session

function ensureTerm() {
    if (term) return term                 // one shell per session, shared
    term = pty.spawn("bash", ["-l"], {
        name: "xterm-256color", cols: 120, rows: 32,
        cwd: "/workspace",
        env: CANDIDATE_ENV,               // HOME=/home/candidate, PATH with claude in it
        uid: 1000, gid: 1000,             // run as candidate, never as root
    })
    term.onData((d) => {
        scrollback = (scrollback + d).slice(-200_000)   // keep the last 200 KB
        for (const c of clients) c.send(d)              // to every tab
    })
    term.onExit(() => { term = null })    // you typed "exit": a new shell next time
    return term
}

// When a browser connects to /pty:
wss.handleUpgrade(req, socket, head, (ws) => {
    ensureTerm()
    clients.add(ws)
    if (scrollback) ws.send(scrollback)   // a reconnect sees what was already on screen
    ws.on("message", (m) => {
        const msg = JSON.parse(String(m))
        if (msg.t === "i") ensureTerm().write(msg.d)        // your keys go in
        if (msg.t === "r") term.resize(msg.c, msg.r)        // your window changed size
    })
    ws.on("close", () => clients.delete(ws))
})

The highlighted lines answer "how does the candidate get a shell": the agent is root, and root may start a program as any user. It starts bash as user 1000, in /workspace, with the candidate's home folder. From then on everything you type, and everything Claude runs, happens as the candidate.

Why reloading the page doesn't kill your work

  • bash lives in the container, not in the page. Closing the tab only hangs up the call; term keeps running.
  • When the page reconnects, the agent replays scrollback, so the screen comes back as it was.
  • Two tabs on one session see the same shell, because every tab is in clients.

Where Claude Code fits in

To the sandbox, Claude Code is just another program, like ls or vim. Typing claude makes bash start it. Its interface (the coloured boxes, the spinner, the diffs you saw) is drawn with the same kind of escape codes, and xterm.js draws them.

How your sign-in worked

  1. The first run of claude in a fresh container finds no saved sign-in and shows its menu. You picked "Claude account with subscription".
  2. It printed a link. You opened it in your own browser and signed in at claude.ai, Anthropic's page, not ours.
  3. claude.ai gave you a code; you pasted it into the terminal. Claude Code swapped it for a sign-in token and saved that in /home/candidate/.claude.

ShipItHQ never sees your password, and the token stays inside your container. When you press Submit, the container (and the token) is deleted, so the next session asks you to sign in again. That is on purpose: Claude Code's terms say a product hosting it may not collect or store people's Claude credentials (chapter 4). It is also why the recording keeps Claude's actions and your typed commands, but not the raw terminal screen: that screen is where the sign-in happens.
