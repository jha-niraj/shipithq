Chapter 1

Opening a workspace

From the moment you press "Start a session" to the moment you see candidate@f65505af9b4a:/workspace$. Three things happen: a computer is built once in advance (the image), a copy of it is started for you (the container), and your browser is connected to it.

Step 0, done once: build the image

Before any session can start, we bake a Linux computer with everything already installed. The recipe is apps/sandbox/image/Dockerfile, and you bake it with pnpm image (which runs docker build). It took a few minutes the first time, because it downloads Node and Claude Code. After that, starting a session needs no downloads at all.

Here is the whole recipe, read top to bottom like a setup guide for a new laptop:

apps/sandbox/image/Dockerfile

# Start from an official image: Debian Linux with Node 22 already installed.
FROM node:22-bookworm

# Install the everyday tools: git, curl, a search tool, a tiny vim, ps.
RUN apt-get update \
    && apt-get install -y --no-install-recommends git curl ca-certificates jq ripgrep less vim-tiny procps \
    && rm -rf /var/lib/apt/lists/*

# Let root run git inside a repo another user owns (the agent commits as root).
RUN git config --system safe.directory '*' && git config --system init.defaultBranch main

# The base image ships a user called "node" (number 1000). Rename it: that is the candidate.
RUN usermod -l candidate -d /home/candidate -m node && groupmod -n candidate node

# Install Claude Code AS the candidate, with Anthropic's own installer. Never modified.
USER candidate
RUN curl -fsSL https://claude.ai/install.sh | bash
ENV PATH="/home/candidate/.local/bin:${PATH}"
# Add our command logger to the candidate's shell (chapter 3), and a git name for commits.
COPY --chown=candidate:candidate bashrc.sh /tmp/bashrc.sh
RUN cat /tmp/bashrc.sh >> /home/candidate/.bashrc && git config --global user.name "Candidate" ...
USER root

# Claude Code's hooks, in the folder Claude Code reads company-wide settings from.
# Owned by root, so the candidate can read them but cannot change them.
COPY managed-settings.json /etc/claude-code/managed-settings.json

# Our agent and its two libraries (node-pty for the terminal, ws for WebSockets).
COPY agent/package.json /opt/agent/package.json
RUN cd /opt/agent && npm install --omit=dev --no-audit --no-fund
COPY agent/server.mjs agent/hook.mjs /opt/agent/
# The starter repo every session begins with.
COPY template /opt/template

ENV DISABLE_AUTOUPDATER=1
EXPOSE 8080
# What runs when a container starts: our agent, as root.
CMD ["node", "/opt/agent/server.mjs"]

So the image already contains: Linux, Node, git, Claude Code (for the user candidate), our agent in /opt/agent, the hooks in /etc/claude-code, and the starter repo in /opt/template. Nothing about your session is in it yet.

Steps 1 to 3 in code: the host server

apps/sandbox/src/server.ts

async function createSession(): Promise<Meta> {
    const id = crypto.randomBytes(4).toString("hex")                // e.g. "425d157a"
    fs.mkdirSync(dirOf(id), { recursive: true })                       // .data/sessions/425d157a/
    await run("git", ["init", "-q", "--bare", "-b", "main", path.join(dirOf(id), "repo.git")])
    fs.writeFileSync(path.join(dirOf(id), "events.jsonl"), "")
    const m: Meta = { id, createdAt: new Date().toISOString(), status: "starting" }
    writeMeta(m)                                                       // meta.json
    await startContainer(m)
    return m
}

Step 3 in detail: the one command that makes the computer

async function startContainer(m: Meta) {
    const name = `sbx-${m.id}`
    await run("docker", [
        "run", "-d", "--name", name,
        "-p", "127.0.0.1::8080",
        "-v", `${dirOf(m.id)}:/root/remote`,
        "--memory", "2g", "--cpus", "2", "--pids-limit", "1024",
        "--label", "shipithq.sandbox=1",
        IMAGE,                                                         // "shipithq-sandbox:dev"
    ])
    const { stdout } = await run("docker", ["port", name, "8080/tcp"])  // "127.0.0.1:32771"
    const port = Number(stdout.trim().split("\n")[0]!.split(":").pop())
    await waitHealthy(port)                                            // step 7
    Object.assign(m, { status: "running", port, container: name })
    writeMeta(m)
}

Every flag, in plain words:

FlagWhat it doesWhy
run -dStart a container from the image and leave it running in the backgroundThe session lives on after this command returns
--name sbx-425d157aGive it a name we can find laterSo Submit can run docker rm -f sbx-425d157a
-p 127.0.0.1::8080Connect a random free door on your Mac to door 8080 inside. The empty middle means "you pick"; 127.0.0.1 means only this Mac may knockMany sessions can run at once without fighting over one number, and nobody on your Wi-Fi can reach them
-v <folder>:/root/remotePlug the session folder on your Mac into the container at /root/remote (a bind mount)Whatever the agent writes there lands on your Mac at once and outlives the container
--memory 2g --cpus 2At most 2 GB of memory and two CPU coresOne session can't slow down the others
--pids-limit 1024At most 1024 running processesStops a "fork bomb" (a program that copies itself forever)
--label shipithq.sandbox=1A sticker on the containerLets us list or clean up every sandbox in one command

Step 6 in code: the agent prepares /workspace

This is the moment the candidate is "given" a workspace. The agent runs as root, so it can create the folder and then hand it over.

apps/sandbox/image/agent/server.mjs

async function setupWorkspace() {
    // Is there already code for this session? (Only after a crash and resume, chapter 3.)
    const resumed = await asRoot(["--git-dir", BARE, "rev-parse", "--verify", "-q", "refs/heads/main"]).then(() => true, () => false)
    fs.mkdirSync(WS, { recursive: true })                       // WS = "/workspace"
    if (fs.readdirSync(WS).length === 0) {
        if (resumed) {
            await asRoot(["clone", "-q", BARE, WS])             // bring the code back
            await asRoot(["-C", WS, "remote", "remove", "origin"])
        } else {
            await run("cp", ["-a", `${TEMPLATE}/.`, WS])        // copy the starter repo in
        }
        await run("chown", ["-R", "candidate:candidate", WS])  // hand every file to candidate
        if (!resumed) {
            await asCandidate(["init", "-q", "-b", "main"])     // git init, as candidate
            await asCandidate(["add", "-A"])
            await asCandidate(["commit", "-q", "-m", "Start: the starter repo"])
            await push()                                        // copy that commit to /root/remote/repo.git
        }
    }
    const head = (await asCandidate(["rev-parse", "HEAD"])).stdout.trim()
    record(resumed ? "session.resumed" : "session.started", { head })
}

asCandidate and asRoot are two tiny helpers. Both run git; asCandidate runs it as user number 1000 (the candidate), so everything git creates in /workspace/.git belongs to the candidate too:

const CANDIDATE = { uid: 1000, gid: 1000 }
const asCandidate = (args) => run("git", ["-C", WS, ...args], { uid: CANDIDATE.uid, gid: CANDIDATE.gid, env: CANDIDATE_ENV })
const asRoot      = (args) => run("git", args)

What you don't see here is just as important: /root/remote, where the recording and the stored repo live. Try ls /root/remote in the terminal and you get "Permission denied". Chapter 4 is about exactly that.

How the page finds your container afterwards

The browser never talks to the container directly. It only knows the session ID. The host server keeps the container's door number in meta.json and forwards each request:

// .data/sessions/425d157a/meta.json
{ "id": "425d157a", "createdAt": "2026-10-03T19:10:42.632Z", "status": "running", "port": 32771, "container": "sbx-425d157a" }
// server.ts: a request for /s/425d157a/agent/files ...
const a = p.match(/^\/s\/([a-f0-9]{8})\/agent(\/.*)$/)
if (a) {
    const m = readMeta(id)                                    // look up the door: 32771
    return proxyAgent(req, res, m.port, rest + url.search)    // ... becomes http://127.0.0.1:32771/files
}

That forwarding is why, in production, the containers can live anywhere (Cloudflare, another server) while the browser only ever talks to ShipItHQ.
