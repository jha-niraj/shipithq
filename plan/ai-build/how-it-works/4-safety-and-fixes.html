Safety, and what we fixed

The candidate has a real shell. Anything their shell can reach, they can read, change or fake. So the design question is always the same: what can user candidate reach, and what can only root reach?

Two users, one line between them

The fix: why the folder moved to /root/remote

This was a real hole in the first version, found by testing it the way a candidate would.

What we built first

The session folder was plugged in at /remote, and the agent ran chmod 700 /remote at start: "only the owner (root) may enter". On a normal Linux server that works.

What the test showed

$ docker exec -u candidate sbx-eca7a687 bash -lc 'cat /remote/events.jsonl'
{"seq":1,"ts":"2026-10-03T19:08:20.545Z","type":"session.started","head":"e2af1726..."}      # could READ it
$ docker exec -u candidate sbx-eca7a687 bash -lc 'echo x >> /remote/events.jsonl && echo "WRITE ALLOWED"'
WRITE ALLOWED                                                                               # could WRITE it

The candidate could read the recording and add fake lines to it, and could have rewritten the stored repo's history. A recording the candidate can edit proves nothing.

Why chmod did nothing

On a Mac, Docker can't run Linux containers directly. It runs a small Linux virtual machine, and the containers live inside that. A bind mount from your Mac therefore crosses two borders: Mac → virtual machine → container. The sharing layer in between presents your Mac's files to Linux and decides their permissions itself; a chmod made inside the container on a shared folder doesn't stick. So /remote stayed open to everyone.

Linux checks every folder on the way down a path. To reach /root/remote/events.jsonl you must be allowed through /root first, and only root is. The shared folder's own permissions never get asked.

The change itself was two lines

apps/sandbox/src/server.ts

-        "-v", `${dirOf(m.id)}:/remote`,
+        "-v", `${dirOf(m.id)}:/root/remote`,

apps/sandbox/image/agent/server.mjs

-const REMOTE = "/remote"
+// Inside /root (mode 700): a bind mount ignores its own chmod on Docker Desktop, so the
+// folder the candidate cannot enter is what keeps the recording and the repo out of reach.
+const REMOTE = "/root/remote"
-    fs.chmodSync(REMOTE, 0o700)

The agent runs as root, so it walks through /root as before. Nothing else changed. Then the same test again:

$ ls /root/remote                     ls: cannot access '/root/remote': Permission denied
$ cat /root/remote/events.jsonl       cat: /root/remote/events.jsonl: Permission denied
$ echo x >> /root/remote/events.jsonl bash: /root/remote/events.jsonl: Permission denied

The broken test session (with its junk line) was thrown away, the image rebuilt, and the host server restarted so new sessions use the new path.

Three quirks your session showed

1. Claude's answers are filed one turn late

Look at what was recorded as Claude's answer after each of your prompts:

Your promptRecorded as Claude's answerReally the answer to
How are you?(empty)
What is this project about...?"I'm doing well, thanks for asking..."How are you?
Hey"This is Notes API, a small HTTP service..."What is this project about?
yes, start on the task"Hey! Do you want me to start on the task..."Hey

Why: the Stop hook fires as Claude finishes, and the agent reads the transcript at that instant. Claude Code hasn't finished writing the last answer to the file yet, so the agent gets everything up to the previous one. On the next turn it picks up the missing answer and files it there.

Fix (not done yet): wait for the transcript to settle before reading it, or read the turn's answer when the next event arrives. Prompts, tool calls and commits are correct; only this one field is shifted.

2. Typing "claude" is recorded when you quit it

Your commands are recorded by bash's PROMPT_COMMAND, which runs when the prompt comes back, after a command ends. For ls that is instant. For claude it is when you quit Claude, so event 19 says you ran claude at 19:23, though you started it at 19:13 (event 3, "Claude Code started", has the right time).

Fix: also record commands as they start (bash's DEBUG trap), or simply rely on claude.started for this one.

3. "Recorded as your edit" when nothing changed

You pressed Save without changing the file. The agent correctly recorded nothing, but the page still said "Saved, recorded as your edit". The page should say "No changes" in that case.

The rules we are working inside

Before writing any code we read Anthropic's published terms for running Claude Code inside another product. Two conditions decide the design:

  • "The Claude Code binary must not be modified." We install it with Anthropic's installer and only add hooks, which is configuration. Its sign-in options are untouched.
  • "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf. Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential." So each person signs in with their own account in their own container, as you did. ShipItHQ never holds the key, never pays for the usage, and never stores the sign-in.

Source: Claude Code's Legal and compliance page, "Can customers offer Claude Code in their products?". That is the "own sign-in" model, and the experiment uses exactly it. If ShipItHQ or a hiring company ever needs to pay for candidates' AI use, the route the same page points to is the Agent SDK with an API key, which means our own chat panel instead of the real Claude Code screen.

Where this leaves us

Proved: a fresh computer per session, Claude Code running unmodified with the person's own sign-in, a real git repo with a commit per turn stored outside the sandbox, and a recording of prompts, tool calls and the candidate's own actions that survives the container. Not built yet, on purpose: the network limits, tamper-proof events, the fixes above, a real database and storage instead of files, Cloudflare instead of local Docker, and a designed interface.
