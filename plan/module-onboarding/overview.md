# Module onboarding - overview

## What this module is

The first thing a user meets when they open a sub-module for the first time:
a short conversation, six to ten questions, that works out where they stand
in that sub-module. Not a static form. Each question is generated from the
user's basic profile and every answer given so far, so the third question
depends on the first two, and a user who has solved two hundred problems is
not asked whether they know what an array is.

It exists for one reason: everything the AI does later in that sub-module
(the DSA mentor, system design reviews, project recommendations) is only as
personal as what it knows going in. Today it knows a semester and a list of
learning goals. After this it knows the user's level, what they have actually
done, what they are weak at and what they want, per sub-module, in the
user's own answers.

The same component, the same server actions and the same prompt serve every
sub-module. Only a module key changes, and with it the focus of the
questions.

Sub-modules at launch:

| key | gate lives on |
|---|---|
| `practice:dsa` | `/practice/dsa` |
| `practice:system-design` | `/practice/system-design` |
| `practice:web-frontend` | `/practice/web-frontend` |
| `practice:web-backend` | `/practice/web-backend` |

## Definition of done

1. A user who has not completed onboarding for a sub-module sees a **gate**
   on that sub-module's landing page instead of its dashboard: what the
   onboarding is for, how long it takes, and one Start button. The dashboard
   is not reachable around it.
2. Pressing Start opens the onboarding **inline in the page card**: a left
   rail with widgets and the current question on the right, in the visual
   language of the signup onboarding. The app sidebar stays.
3. **Every question is generated by AI**, one at a time. The first question
   is generated from the user's stored profile (name, university, semester,
   learning preferences, interests, career goals, work experience) and the
   module key. Every later question is generated from that plus all previous
   questions and answers in this run.
4. Questions are **single choice or multiple choice by default**. The model
   may ask an **open question at most twice per run**, only when options
   cannot capture the answer. Open questions offer a text field and a
   microphone using the Scribe speech-to-text already in the product.
5. The run **ends between six and ten questions**. The model decides when it
   is confident; the server enforces the floor and the ceiling.
6. Every question and answer is **persisted as it happens**. Closing the tab
   mid-run and coming back resumes at the unanswered question. Nothing is
   lost, nothing is asked twice.
7. On completion a **structured profile** is stored per user and sub-module:
   level (`beginner | developing | intermediate | advanced`), facts the user
   stated, strengths, gaps, goals, and three summary lines. The raw turns
   stay alongside it.
8. The user sees a **"where you stand" card** with the level and the three
   lines, then the dashboard. The card remains on the dashboard as a widget
   with a **Retake** control.
9. Retake starts a **new version**. The previous profile is kept, never
   deleted, and remains the current one until the new run completes.
10. A user can **change an earlier answer** from the left rail. Every question
    after it is discarded and regenerated, because they were built on it.
11. The generation runs in a **route handler on gpt-4o-mini** and the median
    wait between answering and seeing the next question is under two seconds
    on a warm route, with a matching skeleton in the question slot while it
    waits. No spinner.
12. The onboarding is **free**. `module_onboarding` is a `0` in the pricing
    table so the decision is visible.
13. The profile is **readable by the other modules**. `plan/practice-dsa`
    PD-6 includes the `practice:dsa` profile in the mentor's system prompt.
14. Each of the five sub-modules has been run end to end in a browser with a
    written note on whether the questions felt specific to that module and to
    the answers given, and every route touched has a matching `loading.tsx`,
    `apps/main` typechecks, `pnpm check-nav` passes, and every text clears AA.

## Out of scope

- **Replacing the signup onboarding.** It stays a static TypeformFlow.
  This module is per sub-module and adaptive; the two share look, not code.
- **Gating pages other than the five above.** `/practice` (the hub),
  `/mock`, `/knowme`, `/ai` are not gated.
- **Acting on the profile.** No checklist, no recommended problems, no
  generated plan at the end. The user lands on the same dashboard as before,
  with a card. Anything that uses the profile is that module's own task.
- **Google speech-to-text.** Scribe is already wired and paid for.
- **Editing the profile fields by hand.** Retake is the edit.
- **Admin views of profiles.**

## Decisions

**Inline in the page card, not a full-screen overlay.** (Niraj, 2026-09-22.)
The gate is part of the sub-module, so the flow renders where the dashboard
would, inside the shell. `TypeformFlow` cannot be reused: it is a fixed
overlay with a static step array, and this flow does not know its next step
until the model answers. A new `AdaptiveFlow` component in `packages/ui`
borrows its easing, layout and choice styling.

**Route handler on gpt-4o-mini, not a worker job.** (Niraj, 2026-09-22.)
The working agreement sends LLM calls to the worker because a request has a
hard budget and the user has already been charged when it dies. Neither holds
here: nothing is charged, the call is a small JSON completion of a few hundred
tokens, and the user is watching the question slot. A job per question would
add a dispatch and a poll ten times per run. If a question generation ever
grows past a few seconds, this decision is the one to reopen.

**All four practice sub-modules plus Projects at launch.** (Niraj,
2026-09-22.) The component, actions and prompt are shared; a sub-module is a
config entry with a key, a label, a focus paragraph for the prompt and a gate
placement. Projects differs only in focus (what has been built, shipped,
deployed) and in where the gate mounts.

**Six to ten questions, the model ends the run.** (Niraj, 2026-09-22.) A
fixed ten forces filler on a confident user. The server holds the floor and
ceiling so the model cannot end at three or run to fifteen. Progress shows
the question number without a total.

**Options by default, open questions at most twice.** (Niraj, 2026-09-22.)
Choosing is faster than typing and yields comparable answers across users.
Open questions exist for the answers options cannot hold ("which problems
did you solve last week") and get the mic.

**Structured profile plus raw turns, level and three lines shown.** (Niraj,
2026-09-22.) The structured fields are what other modules read; the turns
are the evidence; the card is the user's receipt.

**Free.** (Niraj, 2026-09-22.) A mandatory gate that costs credits is the
resume-parse mistake again: charging for something nobody asked for.

**Retake keeps history.** (Niraj, 2026-09-22.) Versions, not overwrites.
The previous profile stays current until the new run completes, so a user
who abandons a retake does not lose their profile.

**Changing an earlier answer discards what followed.** Each question was
generated from the answers before it. Keeping later answers after an earlier
one changes would leave the run internally inconsistent, and the profile
built from it would be wrong in a way nobody could see.

**The profile is a separate table from the practice learner profile.**
`module_onboarding` records what the user said about themselves once, per
version. `practice_learner_profile` (PD-1 in `plan/practice-dsa`) records
what the mentor observed over many sessions and is rewritten continuously.
Different lifecycles, different writers; the mentor reads both.
